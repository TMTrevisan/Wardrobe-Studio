# Comprehensive Code Review & Security Audit — Wardrobe Studio & MCP Server

**Repository:** Next.js 16 + Supabase + Gemini/OpenAI Wardrobe Studio & Hand-Rolled Express MCP Server  
**Date:** 2026-10-06  
**Scope:** `src/app` (all API routes), `src/components`, `src/lib`, `mcp-server/src/index.ts`, `supabase/migrations`, `next.config.ts`, `package.json` files  
**Auditor:** Senior Security Engineer & Systems Architect  

---

## Executive Summary

A comprehensive architectural and security review was conducted across the entire codebase, including all 28 API routes in Next.js, the React client components and Studio workflow, the internal libraries, database migrations, and the standalone Model Context Protocol (MCP) server in `mcp-server/`.

While the application features modern UI patterns and advanced multimodal capabilities (Gemini 3.1 Flash Lite vision classification, chroma-key background removal, and GPT Image catalog reconstruction), the codebase exhibits critical security vulnerabilities, architectural tech debt, and agent-usability deficits:

1. **Severe Authentication Gaps**: The hand-rolled MCP server's `/sse` and `/message` endpoints completely lack authentication, leaving tool execution wide open while `/tools` enforces a Bearer token. Additionally, multiple Next.js API routes (`/api/chat`, `/api/stylist`, `/api/outfits/generate-image`, `/api/outfits/virtual-try-on`, `/api/weather`) are completely unauthenticated and act as free, publicly accessible LLM/GPU proxies using server-side API keys.
2. **SSRF & URL Fetching Vulnerabilities**: Multiple endpoints accept user-supplied image URLs or storage paths and issue server-side `fetch()` requests without validation (`/api/upload/cutout-server`), or implement `assertPublicHttpsUrl()` but specify `redirect: 'follow'` which allows 302 redirects to internal IP ranges (e.g., AWS/GCP instance metadata `169.254.169.254`, loopback `127.0.0.1`). In addition, hostname checks rely on vulnerable prefix matching (`.startsWith(supabaseUrl)`).
3. **Database RLS & Storage Policy Defects**: Permissive development policies on `public.billing_and_token_ledger` allow anyone with the Supabase anonymous key to read and insert ledger records across all users. Recent migrations made the `wardrobe-images` storage bucket private and dropped public insert policies without adding an authenticated insert policy, causing authenticated uploads to fail. Furthermore, the `repair-orphan-images` endpoint leaks unattached files across all users due to a flat storage layout.
4. **Agent Usability Bottlenecks in MCP**: Both MCP implementations execute unbounded `select('*')` database queries, dump entire database tables into LLM prompts without compression or pagination, and return unstructured text-only responses rather than typed, machine-parseable schemas.
5. **Tech Debt & Dead Code**: The Express MCP server lists `@modelcontextprotocol/sdk` and `ws` as dependencies despite never using the SDK and never using realtime subscriptions. The Next.js repository includes heavy unused dependencies (`@gradio/client`, `@huggingface/transformers`), and retains over 2,800 lines of orphaned legacy components replaced by `WardrobeStudio`.

## 1. Critical Severity Findings

### 1.1 Unauthenticated MCP Server `/sse` and `/message` Endpoints
- **File & Lines**: `mcp-server/src/index.ts:348-402`
- **Description**: While `app.get('/tools', authenticate)` and `app.post('/tools/:toolName', authenticate)` are guarded with the `authenticate` middleware, the primary MCP transport endpoints `app.get('/sse')` (line 348) and `app.post('/message')` (line 380) have **no authentication middleware attached**. Any unauthenticated client on the network can establish an SSE connection at `/sse`, receive an active `sessionId`, and dispatch JSON-RPC 2.0 `tools/call` payloads to `POST /message?sessionId=...`. This allows attackers to invoke `delete_wardrobe_item`, `add_wardrobe_item`, and `list_wardrobe` without any Bearer token.
- **Evidence**:
  ```typescript
  // mcp-server/src/index.ts:348-380
  app.get('/sse', async (req, res) => { // <-- NO authenticate middleware
    res.writeHead(200, { ... });
    const sessionId = Math.random().toString(36).substring(2, 15);
    sseConnections.set(sessionId, res);
    ...
  });

  app.post('/message', async (req, res) => { // <-- NO authenticate middleware
    const sessionId = (req.query.sessionId || req.query.session_id) as string;
    ...
    const responsePayload = await handleJsonRpc(payload);
    ...
  });
  ```
- **Remediation**:
  Attach the `authenticate` middleware to both routes:
  ```typescript
  app.get('/sse', authenticate, async (req, res) => { ... });
  app.post('/message', authenticate, async (req, res) => { ... });
  ```
  Note: Because standard EventSource browser clients cannot easily set `Authorization` headers on `GET /sse`, also support query-parameter token validation (`req.query.token === MCP_SECRET`) when the header is absent.

### 1.3 Blind SSRF in Server-Side Background Cutout Route
- **File & Lines**: `src/app/api/upload/cutout-server/route.ts:7-9, 38, 75, 119`
- **Description**: The endpoint extracts `storagePath` directly from the client's JSON request body and issues server-side `fetch(storagePath)` requests on line 75 (for Hugging Face RMBG) and line 119 (for local Python), as well as passing it to `remove.bg` on line 38. There is **no validation** against `assertPublicHttpsUrl()` or any domain check. An attacker can supply `http://169.254.169.254/latest/meta-data/` or internal network addresses (e.g., `http://10.0.0.x`, `http://127.0.0.1:5432`).
- **Evidence**:
  ```typescript
  // src/app/api/upload/cutout-server/route.ts:7-75
  const { garmentId, storagePath } = await request.json();
  ...
  // Line 38: forwarded to remove.bg
  removeBgFormData.append('image_url', storagePath);
  ...
  // Line 75: fetched directly on server without any assertion
  const imageResponse = await fetch(storagePath, { signal: AbortSignal.timeout(15_000) });
  ```
- **Remediation**:
  1. Validate `storagePath` using `assertPublicHttpsUrl()` before fetching.
  2. Better yet, do not accept an arbitrary URL string from the client. Look up the garment's primary image record from `garment_images` in the database and download only from the verified Supabase storage bucket.

### 1.4 SSRF Protection Bypass via HTTP Redirects (`redirect: 'follow'`)
- **File & Lines**: 
  - `src/app/api/items/add-image/route.ts:25, 30-36`
  - `src/app/api/items/search-image/route.ts:194, 209-217`
- **Description**: Both routes run `await assertPublicHttpsUrl(imageUrl)` to verify that the URL is public HTTPS and does not resolve to private or loopback IP ranges. However, both routes subsequently execute:
  ```typescript
  const imageResponse = await fetch(imageUrl, {
    ...,
    redirect: 'follow', // <-- Follows HTTP 301/302/307 redirects automatically
    signal: AbortSignal.timeout(10_000),
  });
  ```
  `assertPublicHttpsUrl()` only evaluates the initial request URL. If an attacker hosts a public HTTPS endpoint (e.g. `https://attacker.com/image.jpg`) that responds with `HTTP 302 Found` pointing to `http://169.254.169.254/latest/meta-data/iam/security-credentials/` or `http://127.0.0.1:3000/api/...`, Node.js `fetch()` follows the redirect into the private network, bypassing the DNS and IP validation.
- **Remediation**:
  1. Specify `redirect: 'manual'` or `redirect: 'error'` on external fetches.
  2. If redirects must be supported, write a custom redirect loop that calls `assertPublicHttpsUrl()` on each successive `Location` header before following.

### 1.5 World-Readable & Writable Billing Ledger via Permissive RLS
- **File & Lines**: 
  - `supabase/migrations/20260627000000_init_wardrobe.sql:71-72`
  - `src/app/api/telemetry/route.ts:32-37`
- **Description**: Migration `20260627000000_init_wardrobe.sql` created:
  ```sql
  CREATE POLICY "Allow public read ledger" ON public.billing_and_token_ledger FOR SELECT USING (true);
  CREATE POLICY "Allow public insert ledger" ON public.billing_and_token_ledger FOR INSERT WITH CHECK (true);
  ```
  Neither `20260715000000_wardrobe_studio_pipeline.sql` nor `20260715063000_wardrobe_studio_policy_cleanup.sql` dropped or scoped these policies. Any user with the Supabase anonymous key can read the entire API consumption ledger, query metadata, cost totals, and inject fraudulent ledger records.
  Furthermore, `src/app/api/telemetry/route.ts:32` exploits this by falling back to `user.client.from('billing_and_token_ledger').select('*').limit(500)` if the query with `user_id` fails, returning cross-user telemetry data.
- **Remediation**:
  Add a migration dropping the permissive policies and binding the ledger to `auth.uid()`:
  ```sql
  DROP POLICY IF EXISTS "Allow public read ledger" ON public.billing_and_token_ledger;
  DROP POLICY IF EXISTS "Allow public insert ledger" ON public.billing_and_token_ledger;

  CREATE POLICY "ledger_owner_select" ON public.billing_and_token_ledger
    FOR SELECT TO authenticated USING (user_id = (SELECT auth.uid()));

  CREATE POLICY "ledger_owner_insert" ON public.billing_and_token_ledger
    FOR INSERT TO authenticated WITH CHECK (user_id = (SELECT auth.uid()));
  ```

### 1.6 Missing Storage Insert Policy on `wardrobe-images` Bucket
- **File & Lines**: 
  - `supabase/migrations/20260715063000_wardrobe_studio_policy_cleanup.sql:16-20`
  - `supabase/migrations/20260715090000_legacy_image_access.sql:6-19`
  - `src/app/api/upload/route.ts:70-75`
- **Description**: In migration `20260715063000_wardrobe_studio_policy_cleanup.sql`:
  ```sql
  drop policy if exists "Allow public read wardrobe-images" on storage.objects;
  drop policy if exists "Allow public insert wardrobe-images" on storage.objects;
  drop policy if exists "Allow public delete wardrobe-images" on storage.objects;
  update storage.buckets set public = false where id = 'wardrobe-images';
  ```
  Migration `20260715090000_legacy_image_access.sql` added a `SELECT` policy (`wardrobe_images_owner_read`), but **never added an `INSERT` policy** for authenticated users on `wardrobe-images`.
  Because `upload/route.ts:70`, `items/add-image/route.ts:78`, `items/search-image/route.ts:242`, `upload/cutout/route.ts:40`, and `upload/cutout-server/route.ts:53` all upload using `user.client` (scoped to the user's JWT), Supabase Storage RLS will deny uploads with `new row violates row-level security policy for "objects"`.
- **Remediation**:
  Create an authenticated `INSERT` policy for `wardrobe-images` on `storage.objects`:
  ```sql
  CREATE POLICY "wardrobe_images_owner_insert" ON storage.objects
    FOR INSERT TO authenticated
    WITH CHECK (
      bucket_id = 'wardrobe-images'
      AND (auth.role() = 'authenticated')
    );
  ```
  Alternatively, migrate all legacy upload routes to use `wardrobe-catalog` or `wardrobe-sources`, which already have user-prefixed RLS policies (`(storage.foldername(name))[1] = (select auth.uid())::text`).

## 2. High Severity Findings

### 2.1 Multi-Tenant Storage Leakage & Image Hijacking in `repair-orphan-images`
- **File & Lines**: 
  - `src/app/api/items/repair-orphan-images/route.ts:39-86`
  - `src/app/api/items/repair-orphan-images/attach/route.ts:14-52`
- **Description**: 
  1. `repair-orphan-images/route.ts:40` calls `user.client.storage.from('wardrobe-images').list('raw')`. Because `wardrobe-images/raw` is a flat directory shared across all users (`raw/{garmentId}-{index}-{ts}.ext`), this lists storage files uploaded by **all users**.
  2. Lines 50-65 only check which paths are referenced by the *requesting* user's garments. Any file uploaded by User B will not be in User A's `referenced` set and will be returned to User A as an "orphan".
  3. `attach/route.ts` takes any `orphanPath` and inserts it into `garment_images` with zero validation of whether the file was originally uploaded by that user. User A can view and attach User B's private clothing photos.
- **Remediation**:
  Isolate storage by user prefix (`raw/${user.id}/...`). Do not allow listing the global `raw/` directory, and verify that any attached path starts with the user's ID prefix.

- **Description**: In `mcp-server/src/index.ts:193`, the `add_wardrobe_item` tool executes:

  const itemData = {

### 2.3 Insecure Domain Prefix Matching (`.startsWith(supabaseUrl)`)
- **File & Lines**: 
  - `src/app/api/ingest/batch-process/route.ts:56-58`
  - `src/app/api/catalog/generate/route.ts:64-66`
- **Description**: To prevent fetching arbitrary image URLs, both routes check:
  ```typescript
  if (supabaseUrl && !img.storage_path.startsWith(supabaseUrl)) {
    throw new Error('Security Violation: image storage domain mismatch.');
  }
  ```
  String prefix checking with `.startsWith()` is insecure. If `supabaseUrl` is `https://xyz.supabase.co`, an attacker who stores a URL pointing to `https://xyz.supabase.co.attacker.com/payload.jpg` or `https://xyz.supabase.co@attacker.com/payload.jpg` will satisfy `.startsWith()`, allowing SSRF.
- **Remediation**:
  Parse the URL using `new URL()` and check the exact hostname:
  ```typescript
  const parsed = new URL(img.storage_path);
  const expectedHost = new URL(supabaseUrl).hostname;
  if (parsed.hostname !== expectedHost) {
    throw new Error('Security Violation: image storage domain mismatch.');
  }
  ```

### 2.4 MCP Server Authentication Fails Open When Env Var Is Missing
- **File & Lines**: `mcp-server/src/index.ts:314-327`
- **Description**: 
  ```typescript
  const MCP_SECRET = process.env.MCP_SECRET || process.env.POKE_API_KEY || '';

  function authenticate(req: any, res: any, next: any) {
    if (!MCP_SECRET) return next(); // <-- FAILS OPEN!
    ...
  }
  ```
  If neither `MCP_SECRET` nor `POKE_API_KEY` is defined in environment variables, the middleware immediately calls `next()`, disabling authentication on `/tools` and `/tools/:toolName`. Combined with issue 1.1, the server runs completely unauthenticated by default.
  Additionally, line 323 uses `token !== MCP_SECRET` (variable-time string comparison) rather than `crypto.timingSafeEqual()`.
- **Remediation**:
  Fail closed if no secret is configured, and use timing-safe comparison:
  ```typescript
  import crypto from 'node:crypto';

  function authenticate(req: any, res: any, next: any) {
    if (!MCP_SECRET) {
      return res.status(500).json({ error: 'Server configuration error: MCP_SECRET is not configured.' });
    }
    const authHeader = req.headers.authorization;
    if (!authHeader?.startsWith('Bearer ')) {
      return res.status(401).json({ error: 'Unauthorized. Missing Bearer token.' });
    }
    const token = authHeader.substring(7).trim();
    const tokenBuf = Buffer.from(token);
    const secretBuf = Buffer.from(MCP_SECRET);
    if (tokenBuf.length !== secretBuf.length || !crypto.timingSafeEqual(tokenBuf, secretBuf)) {
      return res.status(401).json({ error: 'Unauthorized. Invalid Bearer token.' });
    }
    next();
  }
  ```

### 2.5 Global `window.fetch` Proxy Leaks Bearer Token to External Origins
- **File & Lines**: `src/components/AuthGate.tsx:23-46`
- **Description**: `AuthGate` installs a global monkey-patch proxy over `window.fetch`:
  ```typescript
  window.fetch = (async (resource: RequestInfo | URL, config: RequestInit = {}) => {
    ...
    const token = data.session?.access_token;
    if (token) {
      const headers = new Headers(config.headers);
      if (!headers.has('Authorization')) {
        headers.set('Authorization', `Bearer ${token}`);
      }
      config = { ...config, headers };
    }
    return original(resource, config);
  });
  ```
  The proxy does not check whether `resource` is a relative path or an internal API endpoint. If any component or third-party script makes a client-side fetch to Google Photos (`https://photospicker.googleapis.com/...`), CDN assets, or telemetry endpoints, the user's Supabase session JWT is sent in the `Authorization` header to that third-party origin.
- **Remediation**:
  Only attach the `Authorization` header if the destination is a relative path (e.g. `resource.startsWith('/')`) or matches `window.location.origin`:
  ```typescript
  const urlStr = typeof resource === 'string' ? resource : resource instanceof URL ? resource.href : resource.url;
  const isInternal = urlStr.startsWith('/') || urlStr.startsWith(window.location.origin);
  if (token && isInternal) {
    ...
  }
  ```

### 2.6 Non-Atomic Garment Merge Deletes Source Assets via Cascading Delete
- **File & Lines**: `src/app/api/items/merge/route.ts:40-89`
- **Description**:
  1. The route moves legacy `garment_images` from `sourceGarmentId` to `targetGarmentId` (lines 40-53).
  2. It moves `wear_logs` (lines 55-64) and updates `saved_outfits` (lines 66-81).
  3. None of these operations are wrapped in a database transaction (`BEGIN ... COMMIT`). If an error occurs midway, state is left inconsistent.
  4. Crucially, in step 5 (line 85), it deletes the source garment: `user.client.from('garments').delete().eq('id', sourceGarmentId)`.
  5. In the Wardrobe Studio schema (`supabase/migrations/20260715000000_wardrobe_studio_pipeline.sql:102`), `garment_assets` has `garment_id uuid not null references public.garments(id) on delete cascade`.
  6. The merge route **never reassigns `garment_assets`**. When `sourceGarmentId` is deleted, all source crops and catalog cutouts belonging to the source garment are **permanently wiped out** by PostgreSQL cascading delete!
- **Remediation**:
  1. Reassign `garment_assets` to `targetGarmentId` before deleting the source garment.
  2. Implement the merge operation via a transactional Supabase RPC function (`supabase.rpc('merge_garments', { ... })`).

### 2.7 Cross-Garment Invalidation in `set-primary-image` & `delete-image`
- **File & Lines**: 
  - `src/app/api/items/set-primary-image/route.ts:26-29`
  - `src/app/api/items/delete-image/route.ts:21-23, 43-46`
- **Description**:
  - In `set-primary-image`: Line 10 verifies that `garmentId` belongs to the user. Line 20 sets `is_primary_profile: false` for all images where `garment_id = garmentId`. But line 28 updates `.update({ is_primary_profile: true }).eq('id', imageId)` without checking `.eq('garment_id', garmentId)`. A user can pass `imageId` from *another* garment, leaving the first garment without a primary image and promoting an image on a completely different garment.
  - In `delete-image`: Line 21 selects `garment_images` by `.eq('id', imageId)`. It never checks `.eq('garment_id', garmentId)`. Any image belonging to any of the user's garments can be deleted while passing an unrelated `garmentId`.
- **Remediation**:
  Always scope image mutations to both `id` AND `garment_id`:
  ```typescript
  .update({ is_primary_profile: true })
  .eq('id', imageId)
  .eq('garment_id', garmentId);
  ```

### 2.8 Misleading Admin Client in `src/lib/supabase.ts`
- **File & Lines**: `src/lib/supabase.ts:11-17`
- **Description**: The docstring states:
  ```typescript
  /**
   * Service-role / admin client. Bypasses RLS. Only use this when a route
   * intentionally needs to act across all users...
   */
  export const supabase = createClient(supabaseUrl, supabaseAnonKey);
  ```
  `supabaseAnonKey` is the public anonymous key. It does **not** bypass RLS and has no service-role privileges. Any route using `supabase` under the assumption that it bypasses RLS will fail or execute queries with `auth.uid() = NULL`. If a service-role client is genuinely required for background jobs, it must be created with `process.env.SUPABASE_SERVICE_ROLE_KEY`.
- **Remediation**:
  Update documentation and initialize an explicit `supabaseAdmin` client only when `process.env.SUPABASE_SERVICE_ROLE_KEY` is present. Ensure routes that need per-user isolation strictly use `getSupabaseClient(request)`.

## 3. Medium Severity Findings

### 3.1 Event Loop Blocking via Synchronous Child Process (`execSync`)
- **File & Lines**: 
  - `src/app/api/upload/cutout-server/route.ts:147`
  - `src/app/api/ingest/batch-process/route.ts:326`
- **Description**: Both endpoints execute Python background removal scripts synchronously using `execSync(cmd, { stdio: 'pipe' })`. Machine learning models take between 3 and 15 seconds to execute on CPU. Because Node.js is single-threaded, `execSync` completely blocks the event loop, freezing all other incoming HTTP requests, health checks, and concurrent operations until the script finishes.
- **Remediation**:
  Replace `execSync` with asynchronous `exec` or `spawn` from `node:child_process` wrapped in a Promise:
  ```typescript
  import { execFile } from 'node:child_process';
  import { promisify } from 'node:util';
  const execFileAsync = promisify(execFile);
  await execFileAsync(pyBin, [pyScript, tempIn, tempOut]);
  ```

### 3.2 Agent Usability: Unbounded `select('*')` Queries in MCP Server
- **File & Lines**: 
  - `mcp-server/src/index.ts:113, 124`
  - `src/app/api/mcp/route.ts:105-108, 238-243`
- **Description**: In both MCP implementations, the `list_wardrobe` and `fetch_minified_wardrobe` tools execute:
  ```typescript
  supabase.from('garments').select('*').eq('status', 'Active');
  ```
  There is no `.limit()`, no pagination (`offset`/`cursor`), and it retrieves all columns including large JSON blobs (`ai_extracted_json`). As a closet grows to hundreds of garments, this returns megabytes of data, exhausts serverless memory, and overwhelms the calling LLM agent with unneeded data.
- **Remediation**:
  Add `limit` and `offset` arguments to the tool schemas (defaulting to e.g. 50), and select only necessary display columns:
  ```typescript
  let query = supabase.from('garments')
    .select('id, category, sub_category, brand, color_family, fabric_type, fit_block')
    .eq('status', status || 'Active')
    .order('created_at', { ascending: false })
    .limit(Math.min(limit || 50, 100));
  ```

### 3.3 Agent Usability: Dumping Full Tables into LLM Prompts

### 3.4 Agent Usability: Unstructured Text-Only Tool Outputs
- **File & Lines**: `mcp-server/src/index.ts:130-132, 183-185, 208-210, 222-224`
- **Description**: All tools in `mcp-server/src/index.ts` return output strictly wrapped in `content: [{ type: 'text', text: ... }]`.

### 3.6 Unrestricted Wear Logging (CPW Inflation / Deflation Abuse)

### 3.9 `withUser` Helper Drops Route Context (`params`)
- **File & Lines**: 
  - `src/lib/api.ts:22-37`
  - `src/app/api/imports/[id]/analyze/route.ts:58-60`
- **Description**: Next.js route handlers accept `(request: Request, context: { params: Promise<any> })`. The `withUser` wrapper in `src/lib/api.ts` only declares `(request: Request)` and completely ignores `context`. Because of this bug, dynamic routes like `/api/imports/[id]/analyze/route.ts` cannot access `params.id` and are forced to use brittle URL string splitting (`request.url.split('/').slice(-2)[0]`).
- **Remediation**:
  Update `withUser` to accept and forward the context parameter:
  ```typescript
  export function withUser<TParams = Record<string, string>>(
    handler: (args: { user: AuthedUser; request: Request; params: TParams }) => Promise<Response>
  ) {
    return async (request: Request, context?: { params: Promise<TParams> }): Promise<Response> => {
      try {
        const user = await requireUser(request);
        const resolvedParams = context?.params ? await context.params : ({} as TParams);
        return await handler({ user, request, params: resolvedParams });
      } catch (err: any) { ... }
    };
  }
  ```

### 3.10 Weather API Path Traversal & Missing Fetch Timeout
- **File & Lines**: `src/app/api/weather/route.ts:84-85`
- **Description**:
  ```typescript
  const url = `https://api.pirateweather.net/forecast/${apiKey}/${lat},${lon}`;
  const response = await fetch(url);
  ```
  `lat` and `lon` are parsed from `request.json()` and interpolated directly into the URL string without numeric validation or `encodeURIComponent()`. If `lat` contains `../`, it can manipulate the URL path. Additionally, `fetch(url)` has no `AbortSignal.timeout()`, risking thread hangs if the upstream weather service is unresponsive.
- **Remediation**:
  Validate that `lat` and `lon` are finite numbers (`Number.isFinite()`) and pass an `AbortSignal.timeout(10_000)`:
  ```typescript
  const numLat = Number(lat);
  const numLon = Number(lon);
  if (!Number.isFinite(numLat) || !Number.isFinite(numLon)) {
    return fail(400, 'Invalid latitude or longitude.');
  }
  const url = `https://api.pirateweather.net/forecast/${apiKey}/${encodeURIComponent(numLat)},${encodeURIComponent(numLon)}`;
  const response = await fetch(url, { signal: AbortSignal.timeout(10_000) });
  ```

## Conclusion & Next Steps

The repository demonstrates sophisticated styling and vision capabilities, but currently contains critical security vulnerabilities that must be addressed before deploying to any production or multi-user environment:

1. **Immediate Security Fixes (Day 1)**:
   - Add authentication middleware to `/sse` and `/message` in `mcp-server/src/index.ts`.
   - Wrap `/api/chat`, `/api/stylist`, `/api/outfits/generate-image`, and `/api/outfits/virtual-try-on` with `withUser()`.
   - Fix the SSRF vector in `/api/upload/cutout-server` and disable automatic redirect following (`redirect: 'error'`) on server fetches.
   - Patch the Supabase RLS policies on `billing_and_token_ledger` and add authenticated insert policies on `storage.objects` for `wardrobe-images`.
2. **Database & Schema Fixes (Day 2)**:
   - Fix the `raw_image_url` column error in `mcp-server/src/index.ts`.
   - Wrap the garment merge logic in a database transaction that preserves `garment_assets`.
   - Isolate storage paths by user ID in `repair-orphan-images`.
3. **Tech Debt & Architecture (Day 3-5)**:
   - Remove dead dependencies (`@modelcontextprotocol/sdk`, `@huggingface/transformers`, `ws`).
   - Clean up or re-integrate the ~2,800 lines of dead legacy components.
   - Unify the Next.js `/api/mcp` route and the standalone `mcp-server/` onto a single canonical MCP architecture with pagination and structured outputs.
